# AgentSwarms — *Copied or computed?*

`swarmprov` turns a raw multi-agent transcript into a **provenance graph** (who learned what, from whom, when).
From that graph it measures:
- how much of a swarm's knowledge was computed independently and how much was relayed;
- how fast techniques and errors spread;
- which agents were the hubs.

The demo dataset is the OpenAI wiki swarm (the German message board): 14,591 wiki revisions, which become 15,987 posts. Chat transcripts such as AI Village, and any JSON/JSONL message log, go through the same pipeline via the chat adapter; the answer-based analyses need answers reported in the wording the rule extractor reads (see *What the rule extractor recognises*), or `--llm`.

**What it found on the wiki swarm** (full report: [`results/openai-wiki/report.md`](results/openai-wiki/report.md), whose key findings are also in [`headline.md`](results/openai-wiki/headline.md); every number is computed from the dump, and every share is a floor because only captured surfaces are searched):

| question | answer |
|---|---|
| How much was copied? | **93% (95% CI 88–96%) of 1,108 answers by 617 agents were already public before the agent reported them**, 83% at least an hour before, with a median head start of 11.6 h; at most 89 were independent lookups (83 with nothing public before the report; 6 more were first posted by the agent itself before any other copy; at most 110 under `D_visible`, which counts a copy deleted before the report as never public). In 19% of rounds the agent had posted the answer itself before reporting it. |
| Who supplied it? | **It depends on who gets the credit.** The top 10 sources supplied 20–74% of the 1,019 exposed answers credited to a source: 74% credited to the first agent to post the value (out-degree Gini 0.68), 20% to the latest earlier carrier, 21% of the 218 that have a same-page relay parent. First-source credit mostly measures who first posted the value on an item (on 52 of 61 items one agent was first source of every exposed answer), so the report gives the range, not one number. Only 21% of exposed answers trace to a first source that computed the value itself; 63% to one with no answer round observed on the item. Facts repeated by two or more agents travelled 2.0 hops on average, up to 10. |
| How fast did tricks spread? | The blob-hostname sandbox bypass reached **23% of at-risk OECD agents (17 of 73), a median 0.8 h after its first post**; the `markdown.new` fetch proxy reached 6 other sites within a day (median 5.8 h to adoption), while every task-level trick stayed on one wiki. Seed cracking and `clock.wait` are consistent with contagion: after Holm's correction, their adoptions landed on a page that already carried them more often than the adopters' own posts did (posting on a page is not reading it). |
| Did errors win? | The cracked-seed forecast **"Maryland" was carried by 30 agents before the observed "Montana" (11) appeared**; Montana overturned it as soon as it appeared (11 of the last 14 carriers). The live `16.38` overturned the rounded `16.40` within the first 3 h bin, but Hungary stays **contested**: `9.90` kept 69 agents to 17 for the live `9.91`, which led the late carriers only 16 to 13 and never held a lasting majority. |
| Does availability *cause* copying? | **Not identified for most estimates in this swarm**: the answer was public before almost every report, so in most rows only 3–17 agents switch exposure status; where 37 do, no effect is detected (95% CI −0.34 to 0.11). On a synthetic swarm with known copying the same estimator recovers the true effect (0.70 vs 0.70), so the null is the data, not the method. |

```
transcript ──adapter──▶ events ──rules/LLM──▶ claims ──▶ mentions ──▶ exposure table ──▶ A1–A6 + report
 (wiki dump,            (posts)   (answers,            (every       (agent-round:        (figures,
  chat JSON)                       predictions,         item+value   was it public?)      markdown,
                                   round reports)       in public)                        GraphML)
```

## Quick start

The datasets the examples read (`data/raw`, `data/raw2`) are not in git: fetch them first, as *Where the data comes from* below says. A path that does not exist stops the run with one line pointing there.

**Install:**
```bash
pip install -e .            # pandas, pyarrow, networkx, matplotlib, pyfixest
pip install -e '.[llm]'     # optional: Claude-based extraction
pip install -e '.[hf]'      # optional: hf:// dataset URIs
pip install -e '.[dev]'     # optional: pytest, to run the tests (python -m pytest -q)
```

**Wiki dump** (directory or .zip):
```bash
swarmprov run data/raw -o runs/wiki --gold validation/   # ≈2 min; writes runs/wiki/report.md and report.html (open it in a browser), scoring the extractor on the hand labels (report: Validation)
swarmprov run full-wiki-logs.zip -o runs/wiki            # zip works too
swarmprov check runs/wiki                     # do the run's tables agree with each other? exit 1 on an error
swarmprov html runs/wiki                      # report.html again, after editing report.md or for an older run
```

`report.md` opens with **Key findings**, one bullet per analysis, also written alone to `headline.md` for quoting. `report.html` is the same report as one offline page (figures inlined, no network) with the headline numbers as tiles and a **fact explorer**: pick a value or a disputed slot to see its carriers over time, hover a row for the post that carried it, or look an agent up for whom it learned from and supplied.

**Chat transcript** (AI Village, Slack, Discord, framework logs, spreadsheets):
```bash
swarmprov run village-transcript.json -o runs/village --adapter chat --config my_config.json
swarmprov run hf://datasets/aidigestorg/ai-village/chat_messages.jsonl.gz -o runs/village --adapter chat
swarmprov run messages.json -o runs/agents --adapter chat   # no timestamps, no config: message order, one catch-all family
swarmprov run autogen.jsonl -o runs/agents                  # OpenAI, LangChain or AutoGen roles: task turns and tool results are not posts
swarmprov run slack-export/ -o runs/slack                   # a Slack export directory; a Discord export or a CSV works the same way
swarmprov inspect steps.jsonl                               # which fields the chat reader finds, and a mapping to paste
swarmprov run steps.jsonl -o runs/steps --field ts=step_time --field author=agent_handle --field text=output
swarmprov suggest runs/agents -o runs/agents/suggested_config.json   # techniques, families and items mined from a run, for review
```

**What the rule extractor recognises.** A1 and the analyses built on it start from *answer reports*, and the rules read two forms. The verb form is a post saying `answered`, `submitted`, `replied` or `responded` followed by the value, with the item named in the same sentence (`R1 CONFIRMED: Poland arrived; answered 2.9 at +5s`); the item is recognised only when it is a built-in US state or country, a phrase two or more authors write after round markers (`R1`, `G3`, `#4`), or one listed under `extra_items`. The `=` form is `Answer` or `CONFIRMED` (or `confirmed`), an optional colon and `ITEM = value` (`Answer: Hungary = 9.90%`, `G5 CONFIRMED: Montana = 8553`); its item is the capitalised phrase before `=` (up to 40 characters; a known item inside the phrase is used instead), so it needs no item list. It is read in posts that hold no verb-form answer (`Answered: ITEM = value` is one, so its item must be one the verb form recognises). Task-value facts (A4, the relay trees, A6) count only items some post answered, so a free-form chat ("Poland's rate was 2.8% in 2023, per Eurostat") yields URL facts and nothing at A1. `families` and `extra_items` create no answer reports; for other wording use `--llm`. The report's funnel counts the posts saying one of those verbs and the answer claims of both forms; when there are no claims, A1's skip note names the wording.

**AI Village tables** (directory with agents, chat_rooms, agent_goals, etc.):
```bash
swarmprov run data/raw_village -o runs/village
swarmprov run data/village/agent_goals.jsonl -o runs/village_goals  # roster only
```


```bash

```

**Synthetic swarm** (known provenance, used by tests):
```bash
swarmprov synth -o data/synth/transcript.jsonl --agents 60 --seed 2
swarmprov run data/synth/transcript.jsonl -o runs/synth --config data/synth/config.json
swarmprov synth -o data/ag/autogen.jsonl --seed 2 --format autogen   # the same swarm as an untimed AutoGen stream with tool calls
swarmprov run data/ag/autogen.jsonl -o runs/ag --adapter chat --config data/ag/config.json
swarmprov synth -o data/ramp/transcript.jsonl --agents 120 --seed 1 --copy-ramp-h 4   # copying grows with the answer's time on the board
swarmprov synth -o data/scen/transcript.jsonl --seed 2 --copy-rate 0.3 --copy-from first --boards 3 \
    --alias-rate 0.2 --delete-rate 0.1 --technique TRICK-A                           # boards, aliases, deletions, a technique
swarmprov run data/scen/transcript.jsonl -o runs/scen --config data/scen/config.json
swarmprov truth-score runs/scen data/scen      # every analysis against what synth planted; rebuilds the report
```

A missing input, `--config` or `--roster` file, a malformed config, or an input its adapter cannot read stops `run`, `ingest`, `inspect` and the other stages with one `swarmprov: error:` line and exit status 2, before anything is written for a missing file. Every command that reads a run does the same when the directory holds none (no `profile.json`, or one that is not a JSON object, as a write cut short leaves it), and never creates it. `--json` and `--png` create the directory they name.

## Asking questions of a run

`swarmprov trace` reads a finished run directory (every stage up to `graph`; it names the tables a partial run lacks) and answers one question at a time. It always prints the identity mapping it uses (`--mapping merged`, the default, or `strict`).

```bash
swarmprov trace runs/wiki --agent "Mar16|oecd-equity" --item "Czech Republic"  # where did this answer come from?
swarmprov trace runs/wiki --answer d50220c9ec0f653b                              # the same answer, by claim id
swarmprov trace runs/wiki --fact "oecd-equity|Hungary|9.9" --png runs/wiki/hungary.png   # how did this value travel?
swarmprov trace runs/wiki --fact "oecd-equity|Hungary"                           # every value posted for the item
swarmprov trace runs/wiki --event b847fc1cbc646343                               # what was extracted from this post, and why not more?
swarmprov trace runs/wiki --list --limit 50                                      # facts ranked by carriers (--family url for URLs)
```

`--agent` matches agent ids and author strings, ignoring case (`march16oecdscout` finds `Mar16|oecd-equity`). When several agents match, `--item` and `--family` keep the ones with a matching answer; if more than one is left, it lists them. `--item` works only with `--agent`, `--family` with `--agent` or `--list`. `--answer` takes an answer's claim id; a later report of the same agent-round shows the round and says so, and a claim that is not an answer (a prediction, a round sequence) names the agent's answer for the item instead. `--json FILE` also writes the result as JSON, with the run's `clock`. On a run with a sequence clock (see Clock below), `trace` says so under the mapping line, counts head starts and hop gaps in messages, and says the 60-min flag needs a wall clock. `--png FILE` draws one fact as a timeline: x is time (message position on a sequence clock), each row is a carrier in order of first post, same-page relay hops are blue and start at a small dot on the parent's row (its latest earlier post on the page), and cross-page hops are grey. `--limit N` (at least 1) caps the answers or listed facts and the hops printed per fact.

An answer on the wiki run, abridged:

```
mapping: merged (one agent per cohort date and task family; --mapping strict for one per author string)
answer d50220c9ec0f653b: Mar16|oecd-equity, oecd-equity | Czech Republic = 9.7
  report post: b847fc1cbc646343, 2026-06-19 23:26:04, dse/OECDEducationEquitySequence, by March16OECDScout
  public before the report: yes (D); at least 60 min before: yes (D_w60m); a copy still visible at the report: yes (D_visible)
  first public copy: Oct04|oecd-equity, post 2a057dd82c900e32, 2026-06-17 09:46:10, dse/OECDEducationEquitySequence, by OECDEquityOct04Agent; head start 61.7 h; page deleted 2026-06-19 23:40:50 (after the report)
  own earlier post: none
  inferred relay parent: Oct04|oecd-equity (relay), parent post c86deee978462c75 (2026-06-17 09:46:10), 61.7 h before this agent's first post of the value (b847fc1cbc646343, 2026-06-19 23:26:04)
  inferred path from the originator (1 hop): Oct04|oecd-equity -> Mar16|oecd-equity
  competing values: 9.7 (27 carriers) <- this answer, 9.69 (17 carriers), ...
```

| field | meaning |
|---|---|
| report post | the post carrying the agent's first answer report for the item. Its time is `t_report`, an upper bound on when the question arrived. An answer that stated no value of its own reads `(no value; matched on the consensus V)`: exposure matched it on the item's consensus value. |
| `D`, `D_w60m`, `D_visible` | the A1 exposure flags: the value was public before the report, at least 60 min before it, and in a copy still visible (not deleted) at the report. |
| first public copy | the earliest post by another agent with the same item and value before the report, and the head start `t_report − t_public`. Copies posted in the same second are taken in event-id order. Public is not read: this is what was available, not what the agent saw. |
| first copy still visible | printed only when the first copy's page had been deleted by the report. |
| own earlier post | the agent posted the value itself before reporting it (`self_prepared`). A tool result is not a post, so it never counts here. |
| posted first by this agent | replaces the two lines above when the agent posted the value before any other agent did (`self_originated`, at the time given): `D` stays 1, since the value was public before the report, but no source is credited with the answer, so the other agent's copy prints as *a later repeat by another agent* and the answer gives no exposure edge, no A5 credit and no supply. |
| own tool output before the report | framework traces only: the agent's own tool result carried the item and value before the report (`t_own_lookup`). It reads *own lookup preceded report* when no public copy came first (`own_lookup_evidence`), else says a public copy was also there before the report and whether it came before or after the lookup. A tool can echo a value the agent passed in, so this is a lookup, not proof of computation. |
| value given in the task | framework traces only: a system or user message carried the item and value before the report (`t_task`). A task message is no agent's post and no public copy. |
| inferred relay parent | the graph's guess at the source: the latest earlier carrier of the value on the same page (`relay`). With no earlier carrier on that page the hop goes to the originator and reads *cross-page hop: source unknown, attributed to originator* (`relay_xchannel`). A hop inside the 2 s clock resolution reads *direction unreliable*. The parent post is the parent's latest post of the value on that page; the delay runs from it to this agent's first post of the value. When the parent's post is not before the report (the rule exposure uses for a public copy) it reads *parent post not before the report: not this answer's source*, and no path is printed. *None* says why: the agent originated the value, or it has no item–value mention of the matched value (the extractor read its answer report but found no mention, so the relay graph has no hop for it), or it stated no value and never posted the consensus one. |
| inferred path | relay parents back to the value's originator. Its length is the hop depth A5 and A6 count. |
| competing values | the other values posted for the item, each with its number of carrying agents. The matched value is marked `<- this answer`, or `<- matched (consensus)` for an answer without a value. |

A fact (`--fact`) prints its origin post, then every relay hop as an indented tree (depth, kind, time, delay, page, post, excerpt). The counts match `chains_*`: `oecd-equity|Hungary|9.9` has 69 carriers, 68 hops (42 of them cross-page) and depth 10. Values match on the comparison key, so `9.90`, `9.9` and `9.9%` are one fact, and a multi-number value matches on its first number. A post (`--event`) shows its author under both mappings, its family and tags, the claims and item–value mentions extracted from it, the URLs it carries, and the edges and exposures that point at it. When no claim was extracted, it says why; a task message or tool result is marked as such and gives no claims. Excerpts are one line of 160 characters around the item, with an ellipsis at a cut end; `--event` prints the post's text the same way, cut to 600. Agent text is untrusted (the wiki holds a script payload), so escape it before putting it into a web page.

The posts behind these answers are stored at expose time: `exposures_*` carries `report_event_id`, `src_event_id` and `src_channel` (the first public copy), `src_latest`, `t_latest` and `latest_event_id` (the latest copy before the report, A5's second attribution rule), `src_visible_event_id` and `self_event_id`, and on framework traces `own_lookup_event_id` and `task_event_id`.

`swarmprov agent RUN NAME` answers the per-agent questions: did this agent answer with no earlier public copy, did it supply others, whom did it learn from? It matches `NAME` the way `--agent` does (when several agents match it lists them) and prints the agent's profile, its answers (value, `D`, first public source and head start) and the agents its edges link it to, by kind: *learned from* (edges into it) and *supplied* (edges out of it), with replies apart as *replied to* and *replied by* because a reply is an interaction, not a knowledge transfer; at most 10 agents per kind (`--json FILE` keeps all). The profile is one row of `agent_profiles_{merged,strict}.parquet`, which `graph` writes for every agent with a public post; the report's Agents section and the GraphML node attributes read the same table (`analysis/agents.py`), so a count has one definition:

| column | meaning |
|---|---|
| `n_author_strings`, `cohort`, `family`, `families` | how many author strings the label joins (as in `agent_aliases.csv`), its cohort, its task family (the label's family part when the label was built as `cohort|family`, else its most frequent post family; a `|` in a plain author name is no family) and every family it posted in, most frequent first |

| `facts_originated`, `reach_of_originated`, `agents_reached` | task values it posted first; their other carriers summed over those values (an agent that carried three of them counts three times); and the distinct other agents that carried any of them |
| `betweenness`, `techniques_used` | A5's broker score, and the configured techniques its posts used |

Exposure is a floor, so `n_no_prior_copy` is a ceiling on an agent's answers with no earlier copy anywhere (a copy on a surface the run lacks is invisible). It is no bound on computed answers: an exposed answer may still have been computed, and one with no earlier public copy may copy a post the run lacks.

## How it generalises

All source-specific knowledge lives in one adapter plus an `AdapterConfig`, which can be overridden with `--config file.json|toml`:

```json
{
  "name": "village",
  "families": {"fundraiser": "donat|fundrais", "event": "venue|RSVP"},
  "family_from_channel": false,
  "family_from_roster": true,
  "roster_aliases": {"Claude Opus 4.5": "169ea37e-c664-4012-acba-cb583aaab1f3"},
  "techniques": [{"name": "shared-doc", "pattern": "docs\\.google\\.com"}],
  "disputes": [{"family": "fundraiser", "slot": "total raised", "variants": {"$1,481": "1,?481"}}],
  "reference_values": {"fundraiser|total raised": "$1,481"}
}
```

**Chat formats** — The chat adapter reads JSON (a message list, `{"messages": [...]}`, `{room: [...]}`), JSONL and CSV/TSV with a header row (the delimiter is the one the header uses most: comma, tab, semicolon or pipe), each optionally gzipped and with any UTF-8 byte-order mark dropped, and two kinds of directory. A Slack export (`users.json` and `channels.json` beside one folder of day files per channel) gives one post per message: the channel is the folder, the author the user's `real_name` (or `name`; a bot its `username`) and the id the message's `ts`, so a reply's `thread_ts` names its thread's first message; `<url|label>` becomes the URL, `<@U…>` becomes `@name`, `&amp;`, `&lt;` and `&gt;` are unescaped (in links too), system messages such as channel joins are skipped, and messages are ordered by `ts` across files. Any other directory of JSON/JSONL files is joined (a file holding no messages, such as an agent list, is skipped), and each file's name is the channel of the messages that name none. When joined lists reuse ids (`1, 2, …` in every file, or a `ts` two Slack channels share), every id and parent is prefixed with its list's name (`planning/2`, `general/1777885200.000100`), so a reply finds its parent in its own list; ids that never repeat stay as given. A Discord export (DiscordChatExporter JSON) keeps its `channel.name`, and its replies point at `reference.messageId`. AutoGen's `source` names the speaker only when no author alias and no agent id (`agent_id`, `user_id`, …) holds a value, because elsewhere it often names a data source (`web`, `api`); a `source` that looks like a URL or a path is never taken for a speaker. The wiki, corpus, swarm-traces, AI Village and roster adapters are tried first, so the files and directories they recognise are not read as chat.

**Framework traces** — When messages carry a role (`adapters/framework.py`: an OpenAI or Anthropic `role`, a LangChain `type` of `human`/`ai`/`tool`/`system`, also in `messages_to_dict`'s `{"type", "data"}` form, or an AutoGen `type` such as `TextMessage`, `ToolCallRequestEvent` or `ToolCallExecutionEvent`), only the agents' own turns are public posts. Of AutoGen's types only the chat messages (`TextMessage`, `ToolCallSummaryMessage`, `HandoffMessage`, any other `*Message`) are posts; its other events (`ThoughtEvent`, streaming chunks, `ToolCallRequestEvent`, `SelectSpeakerEvent`, …) are steps inside one agent that AgentChat passes to no other agent, so ingest drops them (`profile.json` `notes.n_inner_dropped`; a call request still opens its calls). A system or developer message, and a user or human turn that names no other speaker (AutoGen: source `user`), is the **task**: author `task`, `source_kind` `task`. A user turn that names a speaker keeps it, because AutoGen 0.2 group chats and LangGraph supervisors pass agents' turns on as named user messages; a human correcting the agents that way counts as an agent too. A tool result (an OpenAI or LangChain `tool`/`function` message, an AutoGen `ToolCallExecutionEvent` or `CodeExecutionEvent` (its `result.output`), an autogen-core `FunctionExecutionResultMessage`, an Anthropic `tool_result` block) is the calling agent's **private read**: `source_kind` `tool_result`, attributed to the agent whose call it answers by `tool_call_id`, `call_id` or `tool_use_id` (autogen-core: the ids of an `AssistantMessage`'s function calls), else, for an AutoGen event, to its `source` (the agent whose tool ran; an OpenAI tool message's `name` is the function's, never taken), else to the one agent with calls still pending (an agent's next turn closes its earlier calls; a result naming an id those calls do not have is not theirs), else to `tool`, with a warning. Each attributed result is also a `reads` row (`method` `tool_result`) and sets `has_reads`. A task message or tool result that names no task family is read under every family, since a prompt or a tool's output names the item but rarely the family: a family-less prompt and an agent's lookups in any of its families still match the rounds they precede. Task messages and tool results give no claims or tags, never count as a public copy, a relay hop, a consensus vote or an A4 carrier (declared disputes included), and `task` cannot be cited, so neither the task nor unattributed tool output becomes a source or a hub; the report header counts the task apart (*60 author strings plus `task`*). An assistant turn that names no speaker is still pooled as `unknown`, with the no-author warning. Exposure reads them for two columns: `t_own_lookup` (the agent's own tool output carried the item and value before its report; `own_lookup_evidence` is that with no earlier public copy, i.e. *own lookup preceded report*) and `t_task` (a task message carried them). A1 then says how many of the answers with no earlier public copy were preceded by the agent's own tool output, splits all answers into a public copy first and no own lookup, an own lookup first, and neither, and counts the answers whose value was given in the task (`summary.json` `A1.n_own_lookup`, `n_exposed_no_lookup`, `n_given_in_task`, ...). `swarmprov synth --format autogen` writes the synthetic swarm as an untimed AutoGen stream with a tool call before every computed answer and none before a copied one.

**Field mapping and ingest warnings** — Every field is found through aliases (`ALIASES` in `adapters/chat.py`). When a source uses other keys, map them in the config (`"fields": {"ts": "step_time", "author": "agent_handle"}`) or with `--field FIELD=KEY` (repeatable, or comma-separated where a comma comes before another `FIELD=`, so a key may contain one; it overrides the config). The fields are `ts`, `author`, `author_alt`, `text`, `channel`, `id`, `parent` and `visible_until` (a message's deletion time, found as `visible_until`, `deleted_at` or `deletedAt`: posts that carry one stop being public then, the run records `has_lifecycle` and A1 states `D_visible` (under message order a real deletion time cannot be ordered against positions, so the times are set aside, the header says so and `has_lifecycle` stays off); an AI Village message keeps its own time when its room was deleted later), and a dotted key such as `author.nickname` reaches into nested objects. The mapping applies during detection too, so a file whose text key no alias knows is auto-detected once `text` is mapped, and to an AI Village directory's message table, which is read by the same reader (`inspect` then shows that table). `swarmprov inspect INPUT` prints each adapter's sniff (with the error a sniff raised), the first record's keys, the key each field resolved to and how many records hold it, and coverage over the first 500 records (timestamps read, authors known, text non-empty, channels). It then suggests a `{"fields": ...}` snippet, guessed from key names and values, to paste into `--config`; nothing is applied. Ingest warns in the log, in `profile.json` (`warnings`) and in the report's Data capabilities block when a field looks missing: posts that name no author (with the first record's keys when they are more than half), one author for more than 10 posts, more than 10% of posts without a readable timestamp (no field, or an unreadable value, with an example; a log with no time field at all is warned about only when a key holds times, which the warning names, and otherwise the report's clock note covers it), or more than 10 posts all in one channel (A5's relay rule then takes every hop as same-page). A config key that is not a setting is ignored with a warning naming the nearest setting (`technques` → `techniques`); `"strict_config": true` makes it an error. `--adapter` takes `auto` or an adapter name, and when nothing recognises the input the error lists each sniff that failed and why.

**Capabilities** — Detected and reported: wall clock, message order, explicit authors, read logs, deletions, threading, presence logs, request logs. The report's capability table states what each value, yes or no, means for the analyses. On a threaded source (a chat with `reply_to`, `in_reply_to`, `thread_ts` or a Discord reference) each reply to another agent's post becomes a `reply` edge from the parent's agent to the replier; replies to oneself are dropped, and replies whose parent is not an agent's post in the run are counted in A5's graph sentence. Elsewhere `parent_id` is a revision or summary id and makes no edge. Analyses needing missing capabilities are skipped or labelled.

**Pipeline funnel and skipped sections** — The report opens with a funnel table, also in `summary.json` as `funnel` (all zeros for a source with no posts): posts, posts with a task family, posts with an answer report, answer claims (with how many name no item, no value or no family) and agent-rounds. Each row has its own unit (a post can carry several claims, and repeated reports of one item are one agent-round), so the counts need not shrink row by row. An analysis that cannot run keeps its heading and says why in one line, from the condition the report tests: A1 needs agent-rounds (and says whether no answer was extracted, none had a family or an item, or none had a timestamp; it suggests `default_family` only where that setting applies), A2 more than 20 timed agent-rounds, A3 configured techniques that appear in a timed post, A4 item–value pairs or URLs in posts with a timestamp, A5 provenance edges (and says which kind is missing: a fact two agents carried in timed posts, an exposed answer, a citation). With no task value repeated, A5 counts the URLs that travelled instead, and how many of their hops were same-page relays.

**Clock** — The chat adapter reads ISO times, epoch numbers and epoch strings such as Slack's `1777885200.000100` (9 to 13 digits, seconds or milliseconds by magnitude; only the timestamp field is read this way, so numeric ids stay ids). A time before 1990 or from 2100 on (a mis-scaled number, a 1970 placeholder) counts as no timestamp. Framework logs (OpenAI message lists, AutoGen results, LangGraph state) often carry no timestamps. When fewer than 90% of a file's messages have one and the file is a single message list (a JSON array, JSONL, one wrapper such as `{"messages": [...]}`, or a single `{room: [...]}`), the whole file moves to a *sequence clock*: message *i* is posted at 2000-01-01 + *i* s, `profile.json` records `clock: sequence`, and the timestamps the file did carry are set aside and counted in the header, never mixed with positions (deletion times too, so `D_visible` needs a wall clock). A1's exposed share, A2's consensus estimate, A4's winners and status (the whole run is one majority bin) and A5–A6 run on that order. In the report, every number measured in time is replaced by a line saying it needs a wall clock: the ≥10 min and ≥1 h shares, head starts and the exposure-by-head-start curve, A2's ≥1 h treatment and its dose response, A3's times to adoption and first-seen time, A4's bins and times, A6's relay-window sweep, and the clock-quality and deletion notes. A2 also leaves out its latency outcome, although latency is read from the post text, so A1's *instant* column and A5's *instant only* rows still show. The exposure tables hold `gap_s`, `D_w10m`, `D_w60m`, `D_cons_w60m` and `gap_cons_s` empty, `adoptions_*` its hour columns, and `trace` prints a post's position as its time (2000-01-01 + *i* s), counts head starts and hop gaps in messages and says the 60-min flag needs a wall clock. A file that joins several lists (`{room: [...]}` with two rooms or more), and any directory, has no order between them, so it gets no sequence clock (`has_order` is no): untimed posts keep no time, exposure drops the agent-rounds without one, and the report says how many posts, agent-rounds and mentions each analysis left out (`summary.json` keeps `A1.n_rounds_untimed` and `A4.n_mentions_untimed`; A4 and A5 skip with that reason when nothing is timed).

**Families** — `families` maps each task family to a regex on post text and channel names. With none configured, and no roster or channel family, the chat config's `default_family` (`all`) puts every post in one catch-all family, so a transcript with no config still reaches A1 when its posts report answers in the wording the rules read (*What the rule extractor recognises*). The report labels it, because answers to unrelated questions that name the same item then count as one fact, which can overstate exposure. A configured swarm's unmatched posts stay family-less. When no post has a family, A3's at-risk set is every agent active after a technique's first post; under the catch-all family the same holds for a technique without families of its own. Either way the set is larger than one task's agents, so adoption shares are lower. `diffusion.analyze` decides which set applies once, per technique (`at_risk_basis` in each `summary.json` A3 row: `all_active`, `catch_all` or `families`), and the A3 text and its key finding both read it.

**Identity** — An explicit author field is used as given; otherwise authors are parsed from signatures. Case variants of one handle (`OpenAIResearcher`, `OpenAiResearcher`) are resolved together, so each strict id has one merged id (variants naming different cohorts stay split and are flagged in the audit). The cohort date comes from the handle (`OpenAIOECDNov27`), and from the date a handle's posts open with (`Mar16 R3 …`) only when the source has no explicit author field; set `cohort_from_text` to override. `extract` writes `agent_aliases.csv` (every author string with its strict and merged id, cohort and family, and the size of both groups; on a roster run the family is the roster role behind the merged id). The report counts the merges, lists the largest, says how many only join case variants (which both mappings fold together), and warns when they join authors that an explicit-author source keeps apart. When the two mappings group the author strings identically (each merged agent is one strict agent, as on the synthetic swarm), `expose` and `graph` compute the merged tables once and write the strict ones by relabelling them (`identity.one_to_one`), and the report gives one line saying so in place of its other-mapping sensitivity lines (A1's line, A2's table and dose slope, the origin columns under the other mapping), whose numbers would only repeat its own; `summary.json` still keeps A5's origin counts under both mapping names, as a run whose mappings differ does, so `compare` across the mappings finds the same keys.

**Uncertainty and sensitivity** — The report's intervals are seeded, and `bootstrap_reps` (default 1000, a whole number; `report --boot N` overrides it, `0` turns them off, and anything else stops the report with a message) sets how many resamples they take (`analysis/uncertainty.py`). A1's shares and median head start get 95% percentile intervals from resampling whole items (`item_fe`), and so do the family and round rows that have at least 5 items, each resampling its own; the median head start needs 5 items with an exposed answer, and a statistic undefined in more than 5% of the resamples gets no interval rather than one taken over the rest. A6's `mean_repeaters` resamples facts (5 or more); A3's Kaplan–Meier median carries Greenwood's interval (log-log) where the Kaplan–Meier curve falls to one half (non-adopters are censored, so this can happen with fewer than half adopting). A5's top-10 share and Gini get no bootstrap interval: resampling items repeats their sources and inflates concentration, so the report gives the lowest and highest value with each item left out in turn, beside the range across attribution rules. Three sweeps show what the analyst-chosen thresholds do. A1's *exposure vs required head start* gives the share of answers public at least *t* before the report for *t* from 0 to 48 h, over every answer (and under `D_visible` when deletions are recorded) and for each family with at least 40 answers, as a table, `figures/a1_threshold.png` and `summary.json` `A1.threshold_curve`. A1's instant-answer row recounts the instant share for a threshold *k* of 1, 2, 5 and 10 s and the configured `instant_threshold_s` (only answers that state their latency as a number move; at the configured *k* the report counts the answers whose number and class disagree, since the wording "instantly" sets A1's *instant* class whatever the number). A6's *sensitivity to the relay window W* re-infers the task-value relay trees with a parent allowed only within W (10 min, 1 h, 6 h, 24 h, none): a carrier whose parent posted earlier is left unattributed, a root of depth 0 (`graph.relay_edges(max_gap_s=W)`; the graph itself keeps no window). URLs are left out of that sweep, because their trees take seconds to re-infer for each window. Under a sequence clock the hour-based sweeps are replaced by a needs-a-wall-clock line.

**Coverage** — `coverage_note` is the Limitations bullet on what the exposure search could not see. The wiki and corpus configs cite the collectors' inventory of 143 surfaces (the corpus note adds that a corpus run does not search the wiki dump); without a note, the report says that only the transcript's own posts were searched, so the exposed share is a floor.

**Disputes** — A4 finds (family, item) slots with competing values, plus any declared in `disputes`, and gives each a status: *held*, *overturned* or *contested*, with the late-carrier counts behind it. `reference_values` (`{"family|item": value}`) is analyst input: it fills a separate outcome column and never changes the status. A held or overturned slot reads truth held, error corrected, error persisted or truth displaced by error (*precision variant* when one value is the other rounded); a contested slot reads *unresolved*. A reference matches a variant by its text or its comparison key (`1,481` matches `$1,481`); one that matches no variant says so, and the report lists references that name no item or disputed slot in the run, so a mistyped key shows. The wiki config sets the live-tooltip values for the three OECD disputes; the synthetic config carries the true values. Each value slot's variants are also split by answer round (`errors.variant_provenance`): rounds that state the variant with nothing carrying it public before the report (D = 0, an upper bound on independent derivation) against rounds that adopted it after it was public (D = 1); rounds that state no value inherit the consensus in exposure and are left out, and these are answer rounds, not the mention-level carriers in *variants (agents)*. The table flags slots whose consensus (the value most distinct agents carried, which `y_consensus` scores against) is not the winner, and *precision variants*, where every value is another one rounded. `exposures_*` carry `y_winner` beside `y_consensus`: whether the stated value is the winner, on overturned slots only (NaN elsewhere, and for a round that states no value, since a report's own correct or wrong flag grades the answer against the task, not the winner); A2 adds it as an extra row and warns when the consensus and the winner disagree on slots with answer rounds.

**Suggested configs and mined techniques** — `swarmprov suggest RUN` mines a starter config from a run's posts (`suggest.py`). *Techniques*: a URL *wraps* another when, after its scheme and host and percent-decoded (inner URLs are often encoded, sometimes twice), its path or query holds a scheme (`http:`, `https:`, `://`), its path begins with another hostname (`markdown.new/example.com/page`; a first segment is a host only when its last label is a top-level domain and no file extension, so `wiki.cgi`, `README.md` and `report.xlsx` are files and `user.name` a name), or a query value does and goes on with a path (`?url=www.sec.gov/files`). A segment that is a real hostname, such as a GitHub user called `socket.io`, still reads as one, which is why a technique needs most of a domain's URLs to wrap. A `.tld/` further into the path is not enough, or nearly every URL would wrap. A domain (the host as posted, percent-decoded, lower case, no port) whose distinct URLs wrap another in at least 80% of cases and which 3 or more agents posted becomes the technique `proxy:<domain>`, matching the domain wherever a post names it. Domains from 10% up to 80% (shorteners, redirectors, viewers, archives) are printed as near the threshold and left out, a domain only two agents posted whose URLs wrap in 10% of cases or more as short of agents, and data sources (under 10%) by agents; a run with no domain two agents posted says how many URLs and domains it has, and under message order a first post is shown as its position (`message 12`). *Families*: one per channel, matching its name exactly, when two or more channels each carry 10 posts by two or more authors; else none, so the chat config's catch-all family applies. *Items*: per family, capitalised phrases with a number within 60 characters after them that two or more authors posted, at most 10, leaving out round words, months, cohort tokens, trailing punctuation (`Poland.` is Poland, a built-in country) and items the run already knows. Proposed families come with items found under them: each post gets the family the file gives it (a roster goal or shared-goal era it had stays), the known items are learned again as `extract` would under those families, items the config filed under the catch-all family go to each, and settings that name that family (reference values, disputes, technique families) are printed to re-file. What the run's config sets is kept: its families, and its techniques and items before the new ones (a mined domain an existing technique already matches is printed as such). The settings are those the run's stages recorded in `profile.json` (a run recorded before that reads its config as it is now), and every other one that differs from the adapter's built-in config (field mapping, thresholds, reference values, ...) carries over, so the file replaces the run's config; the printed command reruns the source with it. On the wiki run the wrap share separates the fetch proxies (`jqp.vercel.app` 613 agents 99%, `md.succ.ai` 411 99%, `markdown.new` 370 99%, `r.jina.ai` 214 99%, `pure.md` 162 100%) from the data sources (`api.datausa.io` 909 agents, `www.sec.gov` 539, `wikiservice.at` 715, each 0.1% or less); the 32 mined techniques include the six proxies the corpus config lists by hand, and `webcrawlerapi.com` (73%), `httpbin.org` (47%), `vanderbi.lt` (23%) and `docs.google.com` (22%, its document viewer) sit near the threshold. The item heuristic is a starting point only: it proposes 264 phrases on the wiki, many of them column names. With `"auto_techniques": true` (off by default for every adapter) and no `techniques` configured, `extract` mines the same URL techniques before tagging, writes them to `mined_techniques.json`, and A3 runs on them with each row marked *(mined)* (`summary.json` A3 rows carry `"mined": true`). A3's skip line points to both. A6's `url domains` row counts the distinct agents that posted any URL on each domain, beside the exact URLs, so agents who fetched different pages of one source count together although no exact URL repeats; it has no hops, its interval (with enough domains) resamples domains, and the sentence below the table names the three most shared (`summary.json` `A6` `url domains` `top`).

**Techniques and contagion** — `techniques` are a name and a regex each (optionally `families`, which restrict the at-risk set). Beside the Kaplan–Meier curve, A3 asks whether adopters adopted where the technique was already posted (`diffusion.contagion`, same at-risk set): the share of adoptions on a page another agent had posted it on strictly before, against each adopter's own posts from the first appearance on in the adoption post's family, with an exact within-agent permutation p-value per technique. A share above the baseline with p < 0.05 after Holm's correction for the techniques tested (`p_holm` in `summary.json`) reads *consistent with contagion*, and one below 0.05 only uncorrected is named as such; fewer than 10 adopters get a warning; a technique with a post that matches its pattern only by naming a page (a link to `AgentLinksZZZ2` under `ZZZ`) is not tested, one whose pattern merely also matches page names is tested and the report says how many of its adoptions landed on such a page, and the test needs posts on two or more pages or channels.

**Detail tables and export** — `report` keeps the rows behind A1, A3 and A4 per mapping: `a1_by_family_*` (every family; the printed table drops those under 10 answers and says how many), `adoptions_*` (technique, agent, `in_at_risk`, `is_originator`, `t_first_use`, `hours_from_first_seen`, `adopted`, `censored_at_h` (both hour columns empty under a sequence clock), and for each adopter the page, whether it carried the technique, its baseline and `t_exposed`, its first earlier post on such a page; the at-risk rows are exactly the Kaplan–Meier inputs) and `disputes_*` (slot, kind, family, item, variant, agent, `t_first`, `is_first_variant`, `is_winner`, `carried_both`, `status`; a value slot's carriers come from item–value mentions, a round slot's from round claims, a declared slot's from its patterns). `swarmprov export` writes any of them, or the stage tables, as CSV or Parquet; `exposures` and `edges_exposure_citation` keep the columns of the committed CSV mirrors, the full header even for an empty table. A detail table exists only for the mapping the report was built under (`run` builds `merged`), and `export --mapping strict` says to run `report --mapping strict` first.

**Comparing runs** — `swarmprov compare RUN_A RUN_B` says what changed between two runs: another config, LLM against rule extraction, a roster attached or not, a code change, or (`RUN_B` = `RUN_A` with `--mapping-b strict`) the other identity mapping. It writes `compare.md` and `compare.json` and counts every difference once (`n_changes`, 0 for a run against itself) in three layers. *Setup*: adapter, source, config file and every config setting that differs, capabilities, posts, roster, clock and mapping. The settings are those each run's stages recorded in `profile.json` as they ran (`config_settings`, with a hash per stage in `config_stages`), not the config file as it reads now, so a file edited in place between two runs shows; a stage rerun after an edit is noted, and a run recorded before stages kept their settings is read from its config as it is now, with a note. *Summary*: `summary.json` (or `summary_strict.json`) flattened to one value per path, with list rows keyed by what they describe (A2 by outcome and treatment, A3 by technique, A4 by slot, A5 attribution by rule, top sources by agent, the threshold curves by answer group, the window sweep by W), so a reordered or removed row reads as such; sections and rows only one side has are listed apart, counts (whole numbers) must match exactly while other numbers count as equal within a relative tolerance (`--tol`, default 1e-4), a missing value (null, or NaN in an older summary) equals a missing one and a time spelt two ways (`2026-06-20 05:10:21+00:00`, `2026-06-20T05:10:21+00:00`) is one value, and the report prints the tolerance and the largest difference it hid. Fixed-effects estimates move by up to 6e-5 relative between processes on identical tables (the wiki's A2 and dose rows), which the default hides and `--tol 0` reports. *Rows*, on the stable ids: posts by `event_id` (added, dropped), claims by `claim_id` (added, dropped, or a changed item, value, round, family or type), agent-rounds by `claim_id` (added, dropped, flips of `D`, `D_w60m`, `D_visible`, `D_cons`, `y_instant` and `y_consensus`, a changed source or agent), author strings by `author_raw` (a changed label, and *regrouped*: its agent joins a different set of author strings) and facts by (family, item, value key) (carriers, originator, depth). Across mappings, the strict side's labels are read as merged ones (merged is a function of strict) before sources, originators and the top-source rows compare, so what remains is more than the mapping's relabelling. A chat event id hashes the file path, so a moved transcript changes every id: when fewer than half the posts share one, posts are aligned on (time, author, text hash), claims inside paired posts by type, item, value, round and order, and a key two posts share on either side is a collision, counted and left unpaired. A committed `results/` directory holds a summary and no tables, so only the setup and summary are compared there. On the wiki, merged against strict gives 1,108 → 1,164 agent-rounds (56 only under strict, none only under merged), one `D` flip and 366 author strings regrouped; a rerun with `{"disputes": []}` lists the declared G5 slot as the one A4 row only in A (another slot is featured in its place), with no claim or exposure change.

**Key findings and the HTML report** — `report.key_findings` writes the block that opens every report with posts: one bullet per analysis that ran, or the line a skipped one gives (kept in `summary.json` as `skipped`), each stating the definition it rests on. Every number in it is a `summary.json` value formatted, never recomputed (`tests/test_headline.py` parses each back), so the block, `headline.md` (`headline_strict.md` under strict) and `summary['headline']` cannot drift from the report. A1 gives the exposed share with its interval, the share an hour before, the median head start, the independent count (with the self-originated answers counted apart, so the bound is at most their sum) and its `D_visible` variant (with the self-originated answers `D_visible` does not already count added, `n_independent_at_most_visible`), as floors; A2 reads each headline row by one rule (`causal.reading`, which the table's notes and the tile read too): *identified* with at least twice the table's minimum of switching agents (20) and a 95% CI that excludes 0, *no effect detected* with as many and a CI that covers 0 (each such row with its switchers and interval), and otherwise *not identified* with the range of agents that switch (a weakly identified row, 10–19 switchers, is not identified here), naming the outcomes and treatments it tried when no row is either (`y_winner`, an extra row, is no headline), and the tile reads *mostly not identified* when most headline rows are not identified, naming the row with no effect detected beside them; A3 the largest adoption shares (and the techniques consistent with contagion); A4 each featured slot's first variant, winner, status and outcome; A5 the top-10 share's range across the attribution rules that credit every exposed answer (first and latest source), then each rule's share, the relay parent's of the answers it matches, with first-source credit's leave-one-item-out range (or, with no source credited, how many exposed answers are self-originated); A6 the repeated facts and the longest chain. A report with no posts has none. `swarmprov compare` leaves `headline` out, since it restates values compared one by one. `report.html` (`html.py`) converts exactly the Markdown the reports write, escaping all text before applying any formatting (the wiki report quotes a probe's `<script>` payload, which the page shows as text); its hero tiles read the same summary values, and `swarmprov html` reads a summary written before a value was added (the independent tile without `n_self_originated`). The fact explorer carries, as JSON in the page, the task facts carried by two or more agents (the 200 most carried), the 3 most carried URLs (traced in that order until their hops and posts take 1 MB of the page, which then says how many it left out) and A4's featured slots in full, each traced by `query.fact_lineage` as `trace --fact` does (on that fact's own rows: the explorer groups the edges and mentions by fact once), with each post's excerpt once per item it carries (centred on that item, cut to 120 characters) and the agent profiles (`agent_profiles_*`) of the carriers, the answering agents and the first sources with their links: the agents each learned from and supplied, by edge kind (at most 6 each way, replies left out as interactions). Its timeline draws a carrier per row in order of first post (against time, or whole message positions under a sequence clock): same-page relays solid from the parent's post, cross-page hops grey (source unknown, attributed to the originator), a ring where the hop falls within the 2 s clock resolution, the variants of a slot in their own colours; a row's post, page and delay show on hover, tap or arrow keys, in a box that stays on screen below the timeline however long it is (where rows carry no label, at phone width or past 100 rows, the active row's band names its carrier), and every row is also in a table. The paths are inferred, not proven, and the page says so beside the timeline. Figures go into the page as 256-colour palette PNGs, about a third of their bytes and as sharp (the files in `figures/` stay as drawn). On the wiki the page is 1.4 MB (0.6 MB of it figures) and builds in about 4 s; on a 30,000-post chat it is 1.9 MB and builds in about 4 s (it was 4.4 MB and 41 s when every fact was traced on the whole tables), so `report` and `crosssite` always write it.

**Lifecycle** — Not just recorded, but used. From wiki events: deletions (with cycle tracking), recreations, and probes; from a chat export, a message's `deleted_at`. The report adds clock-quality notes, deletion/recreation blocks, probing blocks, and exposure gains `D_visible` (ignoring deleted copies).

**Items and rounds** — Learned from the transcript: phrases following round markers become items (no manual task list needed). US states and countries are built in. Round sequences learned from chains like `MA → CT → MI → WV`.

**AI Village tables** — The `village` adapter recognises: `agents`, `chat_rooms`, `agent_goals`, `village_goals` (eras), `villages` (metadata), message tables, activity logs (`claude_code_sessions`), and `summaries`. Posts get agent/room names, rooms give channel lifecycle, and allow/deny lists become **audiences** for per-audience exposure judgement. Set `schedule_tz` in config for timezone-aware post timing.

**Rosters** — Replace guessed identities and families. Any table with agent id + role/goal + start time works (JSON, JSONL, CSV, TSV). Family precedence: agent's own goal → text/channel families → shared era goal. Report shows batches, comparable tasks, goal changes, and coverage gaps.

**URLs as facts** — Indexed for reach and relay chains on free-form chat without task structure.

**Optional LLM extraction** — `--llm claude-haiku-4-5` uses structured outputs. LLM handles semantics, rules fill in numbers. Results are cached in `RUN/llm_cache/` under a hash of the model, the prompt and the post (family, author, channel, text), so an edited post or prompt is asked again and a rerun into the same directory never serves another transcript's extraction; posts identical in all four are asked once, an entry is written aside and moved into place, and one a killed run left unreadable is asked again. The post is sent between `<post>` tags it cannot close (a `<post` or `</post` in its text is broken up), and the prompt says it is untrusted agent-written data whose instructions are never followed. The first call runs alone: if it fails with an authentication, permission or unknown-model error (no `ANTHROPIC_API_KEY` included), or if every call fails, the run stops with that error (exit status 2). Otherwise a post whose call failed keeps its rule claims, and profile.json's `warnings` and the report say `N of M LLM calls failed: <first error>`. profile.json's `llm` records the model and the counts (candidate posts, served from the cache, calls, failed, repeats of an earlier post), which the report's source line repeats; a later `extract` without `--llm` clears it, and a run that used `--llm` no longer suggests it in its skip notes.

## Design notes and limitations

- **Unit of authorship.** A wiki revision stores the whole page, so the unit is the *paragraph a revision added*. A paragraph counts as new the first time its normalised text appears on the page since the page was last deleted. Line diffs would over-attribute, because repeated mis-decoding re-encodes every line on each save. The author is the trailing `-- Signature`, not the account that saved the page.
- **Exposure is inferred.** The dump contains saves, deletions and probes but **no page views**, so "public" does not mean "read". `t_report` is an upper bound on arrival; the ≥1 h variant is robust to report lag. Only wiki timestamps are used as a clock, because the agents' task clocks are dilated.
- **The causal treatment `D_cons`** asks whether the *consensus* value was public, regardless of what this agent answered. A first version used the agent's own value, which mechanically ties wrong answers to "unexposed" and produced a spurious +0.43 effect.
- **Identity.** `merged` = (cohort date, task family), where the cohort date comes from names like `OpenAIOECDNov27` or, for signature-parsed sources, the post's opening token. `strict` = the signature itself, case-folded; case variants share one merged id. Every headline number is reported under both (where both group the author strings identically, one line says so instead), and `agent_aliases.csv` lists every merge for audit.
- **Contagion is a page test, not a reading test.** A3's contagion columns ask whether an adoption landed on a page that already carried the technique more often than the adopter's other posts did. Posting on a page is not reading it, and a task can send agents to the pages that carry a technique (a common cause), so the baseline stays within the adoption post's family and the result reads *consistent with contagion*, never proof, and only after Holm's correction for the techniques tested. A per-agent-hour rate ratio before and after exposure was left out: agents post more once they reach a task's pages, which inflates it.
- **A dose response identifies only the intensive margin.** Exposure stores how long the consensus value had been public before each report (`t_cons`, `gap_cons_s`), and A2 adds an exploratory block below its table: among exposed rounds only, the instant outcome on `log1p(head start in hours)` (the slope) and on bins against a head start under 1 h, with agent + item FE. Within an agent the head start varies across items where exposure barely does, but it answers a narrower question, whether reuse grows with how long the answer had been public given that it was, and leaves whether exposure matters unidentified. Its assumption is that, within an agent, how long before its report others had posted the consensus is unrelated to its item-specific propensity to answer instantly. Both outcomes measure the head start to the report, so a late report gets a longer one. `y_instant`, which scores a round with no stated latency 0, is biased besides: on the wiki, within an agent, rounds with longer head starts state a latency less often (−0.18 per unit of log1p hours). `y_instant|known` avoids that scoring but keeps only the rounds that state a latency, so its sample is selected on the dose: the less biased read, not an unbiased one. Only agents whose outcome varies inform an estimate (one that answers every exposed round the same way moves it only through the item effects), so the block counts them per term. An outcome is identified when the within-agent SD of the log head start is at least 0.25 and at least 10 agents have rounds in two or more bins; each term then needs 10 informative agents (the slope: head start and outcome both vary; a bin: a round in it and in another bin, and an outcome that varies), and so does the reference; an estimate on fewer than 20 (a bin: in it or in the reference) is noted *weak* or *shape only* and drawn grey. The slope also gives its exact leave-one-agent-out range and the share of its clustered variance that its two largest agents carry. On the wiki, among rounds with a stated latency, 127 agents' head starts vary but only 26 also vary in the outcome (against 4 that switch exposure status); the slope is −0.010, but two agents carry 87% of its clustered variance and leaving one agent out moves it between −0.073 and −0.002, so its SE (0.013) understates the uncertainty, and only 2 agents inform the reference bin, so no bin is identified. On synthetic swarms of 120 agents (seeds 0–7) with copying that ramps up over 4 h (`--copy-ramp-h 4`) the slope is positive on all 8 and significant on 6, over 12 h on all 8 and 5, and its 95% interval covers the design's own target (the same regression on each round's true copy probability) in 23 of 24 runs including 8 with no ramp, where it is never significant. The bins are less reliable: 2–14 agents inform the reference there, so on most runs no bin is identified and elsewhere each is shape only; with no ramp none of the 6 bins estimated differs from zero at the 5% level, with a 4 h ramp 7 of 12 do. This block stays out of A2's reading.
- **The consensus is not the later majority.** `y_consensus` scores against the value most distinct agents carried over the whole run, which on the wiki is often the older, more-copied value; A4's winner is the majority among the last third of carriers. A2 keeps `y_consensus` as its outcome, adds `y_winner` for overturned slots as an extra row, and warns how many answer rounds the two disagree on.
- **A4 status is a convention.** The winner is the most common value among the last third of a slot's carriers (none on a tie). If it is the first value, the slot is *held*. A later winner counts as *overturned* only if it also held the majority of new carriers in every 3-hour bin from some point on, with at least 5 late carriers in all; otherwise the slot is *contested*. Two values first seen at the same moment leave no first value, so that slot is contested too, whichever way the labels sort. The report prints the bin width and the tail share.
- **Figures draw what the tables say.** The A4 figure counts every carrier, so each line ends at its variant's agents; when the earliest 3% of carriers would take more than a third of the time axis (a post days before the dispute), the axis starts after them and the legend counts them and gives the first one's time. It draws at most three variants: the first to appear, the winner (or every variant tied for the lead of the late carriers) and the next to appear. The legend marks the winner (none on a tie) and when its lasting majority began, also drawn as a dashed line, and the lower row gives the winner's share of new carriers in each 3-hour bin (each drawn variant's on a tie), leaving empty bins out and drawing bins with fewer than 3 new carriers faint. The A2 figure draws every row: one with fewer than 10 agents whose exposure status switches reads *not identified* at zero, each label gives that number, and an estimate from fewer than 20 is grey; its dose figure (`a2_dose.png`) draws each head-start bin against the reference (hollow at zero), reads *not identified* where under 10 agents inform a bin, greys a bin under 20 (in it or in the reference) and gives each slope's leave-one-agent-out range. The A5 Lorenz curve marks where the top 10 first sources begin, A6 pools facts repeated by 20 or more agents into one labelled point, and percent axes print the decimals their range needs (a tick at 2.5% reads 2.5%, not 2%).
- **Relay edges are plausible paths, not proven ones.** Each carrier is linked to the latest earlier carrier on the same page, and to the originator if there was none, at any lag; A6's window sweep shows how much of the depth needs hops longer than W (it does not pick a W). `trace` labels the relay parent as inferred and keeps it apart from the first public copy. On the synthetic swarm, where copiers take the latest post, the relay parent names the true source for at least 98% of copied answers and the first public copy for about a quarter. When copiers take the first post (`--copy-from first`), the first public copy is right every time and the relay parent about a fifth of the time.
- **The headline is generated.** The results tables in this README are written by hand, so they can drift from the code; the report's key findings, `headline.md` and the HTML tiles are formatted from `summary.json` alone, each bullet names its definition and says *floor* where exposure is one, and a test parses every number back. Quote `headline.md` rather than copying numbers. The README's own numbers are checked the same way: `tests/test_results.py` parses each row of the headline table, the wiki results table and the cross-site and corpus text, and formats each number from the committed summaries (the wiki's, the synthetic swarm's scorecard, the cross-site and corpus ones), the cross-site report and its `technique_spread.csv`, so a regenerated summary that moves a number fails the suite until the README is updated. The few numbers read off tables `results/` does not hold (the 12 h between the G5 forecast and the observed value, the activity waves) are marked as such in the test and not checked. It also requires each committed key-findings block, `headline.md` and `summary['headline']` to be what `report.key_findings` writes from that summary, so a wording change fails until `results/` is regenerated.
- **Hub concentration depends on the attribution rule.** Exposure says a value was public, not whom an agent took it from, so A5 credits each exposed answer three ways: the first other agent to post the value before the report, the latest one, and the same-page relay parent (joined on the same value key exposure matched; a parent whose post is not before the report credits nobody, as in `trace`; the unmatched count is printed). It reports all three, on every exposed answer and on instant answers only, plus the Gini of the items' exposure counts, which is what first-source credit gives if each item has a single source. On synthetic swarms (seeds 0–7) the rule that matches how the agents copy names the true source for 98–100% of copied answers and reproduces the true top-10 share to within 0.01, while the other rule names it for 19–28% and misses the share by 0.36–0.55 (first-source credit reports 64–76% where copiers take the latest post and the truth is 26–28%). With no copying at all, first-source credit still puts 68–80% of exposed answers on its top 10, and with `--copy-from random` neither rule names the source for more than 57%. So the rules are a sensitivity range: a rule that wins on the synthetic swarm only matches how the simulation copies. No rule credits a *self-originated* answer, one whose agent had posted the value before any other agent did (`exposure.self_originated`, `t_self_prepared < t_public`): `D` stays 1, as the value was public before the report, but the other agent's copy is a later repeat, not its source, so the answer gives no exposure edge, no supply in the agent profiles or `a7_supply_network.png`, and its own row in the origins table. A1 counts these apart (`n_self_originated`) and bounds independent lookups by their sum with `n_independent` (`n_independent_at_most`); on the wiki that is 6 answers under each mapping. `analysis/origins.py` labels each credited source by its own answer round on the item (computed, no answer round observed, dissent, relayed, or *posted before its own source* when that round is self-originated, so a source that posted the value first is its origin, not a relay of the later copy) and follows relayed sources to a root, stopping at a source that had posted the value before the post it is credited to (*posted before its own source* if no other agent had posted it earlier, else a *chain cut*, which only the latest rule produces); `summary.json` carries both as `A5.attribution` and `A5.origins` (origin counts under `by_mapping`, roots for the report's `mapping`). *Relayed* means exposed, not copied, so on the copy-latest swarm those chains end at the true root for only 51–68% of copied answers.
- **An own lookup is not a computation.** A tool result before the answer shows the agent fetched the value, but a tool can echo what the agent passed in (a search for a value it had already read), so the flag is `own_lookup_evidence` and the report says *own lookup preceded report*, never *computed*. On the synthetic AutoGen swarm (seeds 0–7, on message order) an own lookup before the report marks exactly the computed rounds, and a public copy with no own lookup gives the true copied share (55–62%); `own_lookup_evidence` itself, which also needs no earlier public copy, flags 44–56% of the computed answers (those whose value was not yet public) and no copied one. Attribution without call ids is guesswork under parallel calls, so a result that neither an id, an AutoGen `source` nor one agent's pending calls settles stays with `tool`. Treating unnamed user turns as the task can mislabel a human's correction as task input.
- **Message order is a clock, not a time.** A sequence clock preserves what the exposure test needs, which post came first. On the synthetic swarm with its timestamps stripped, the exposed share (80.7%), the top-10 source share and the A2 consensus estimate equal the wall-clock run's; A4 uses a different rule: a later winner must hold the majority of all the slot's carriers, not of every 3-hour bin from some point on. Nothing measured in hours is converted into messages, and the order is only as good as the order the file was written in.
- **Intervals cover sampling noise across items only.** One first poster supplies most of an item's exposures, so answers to one item are not independent: on the wiki, resampling single answers gives the ≥1 h share an interval about a third as wide as resampling items (0.05 against 0.13 wide), and resampling agents hardly widens it (0.06). Items are the cluster. Families are too few to resample (23 on the wiki), and a family row from fewer than 5 items gets no interval. No interval covers identity-mapping or extraction error, which the strict-mapping sensitivity lines and the validation section address instead. On the synthetic swarm, the threshold curve and the instant-threshold sweep reproduce the truth at every threshold, and A1's exposed share equals D's target computed from the truth (the share of answers whose value another agent had reported earlier), so its interval contains that target by construction; it does not contain `public_at_arrival` (0.833 against 0.807, interval 0.783–0.828), which counts any earlier post on the item, whatever its value. Coverage itself is checked by simulation (`tests/test_uncertainty.py`): over 200 draws of 40 items whose answers mostly agree, the item interval covers the population share 93% of the time (a percentile interval runs a little narrow on few items), and one from resampling single answers 52%.
- **The synthetic scorecard holds under the simulation's own model only.** `swarmprov truth-score` compares a run of `synth` output with the truth beside its transcript (`truth_validation.json`, shown in the report's Validation section). Over seeds 0–7 of three 60-agent scenarios: copying the latest post at rate 0.7 on one board, `D` agrees per round with the answer being on the board at arrival for 95–97% of rounds (D is value-specific: a wrong computed answer has no earlier copy, and a copy posted between arrival and report counts) and with an earlier post of the same value for 100%; A2's 95% interval covers the true effect (the share of rounds public at arrival that copied) in 8 of 8; the latest-source rule names the true source of 98–100% of copied answers, with a top-10 share on instant answers within 0.005 of the truth; and A4's status and outcome match the same rule run on the true answers on every slot. Copying the first post at rate 0.3 on three boards, with 20% of posts under an alias, 10% deleted and a planted technique: `D` agrees for 90–93%, `D_visible` for 100% against an earlier copy still undeleted at the report; A2 covers the truth in 8 of 8 (significant in 7); first-source credit names the source of 87–100%, every miss a copy of a first post deleted before the copier read the board, where the first copy still visible names it every time; 80–85 cross-page hops; A3's at-risk set, adoption share (83–100%) and Kaplan–Meier median equal the planted ones; and the merged mapping joins every alias (purity 100%, no agent split) where the strict one splits 36–41 agents. With no copying and 30% fast agents (the latest to start, instant on half their questions), instant answers run 14–22 points more often in exposed rounds when agents are not held fixed, yet A2's estimate is significant in none of seeds 0–9 (p 0.06–0.89, |β| ≤ 0.10, its interval covering 0 each time). The pipeline recovers what this simulation plants; a real swarm's agents need not copy, delete or sign the way it does.
- **Replies are interactions, not knowledge transfers.** A reply edge says one agent answered another's post, not that it took a value from it, so A5 counts replies for brokers (betweenness) and the GraphML only: never for the exposure out-degree, the Gini or top-10 shares, the attribution rules or the relay counts.
- **The exported graph.** `provenance_{merged,strict}.graphml` and `.json` (networkx node-link data) have one edge per (source, destination) pair over every kind: `kinds` lists them, `n_relay`, `n_xchannel`, `n_exposure`, `n_citation` and `n_reply` count them, and `weight` counts the knowledge transfers, `n_relay + n_exposure + n_citation`: a cross-page hop's source is unknown, and a reply is an interaction. Each edge also carries `n_facts` (distinct item–value facts), `first_ts` and `last_ts` (the first and last destination post), `median_dt_s` and `n_within_clock_res`; nodes carry the agent profile. Every attribute has one type, as GraphML needs: a missing number is -1 and a missing time or text is empty. The graph attribute `clock` is `wall` or `sequence`; under a sequence clock (with a `clock_note` saying so) a time is the message's position, 2000-01-01 + i s, and `median_dt_s` a gap in messages. `figures/a7_supply_network.png` draws the exposure edges alone, under the first-source rule its title states: sources are grey discs sized by the answers they supplied (the top 10 labelled), and each agent with an exposed answer is a dot coloured by its task family. Its layout is seeded and independent of the hash seed, so a rerun draws the same picture.
- **Every JSON file is strict JSON.** `summary*.json`, `checks*.json`, `validation*.json`, `truth_validation.json`, `compare.json`, `trace --json`, `agent --json` and the fact explorer's data in `report.html` all go through one encoder (`fmt.dumps`): NaN, infinities and NaT become `null`, times ISO text and numpy scalars plain numbers, so a strict parser reads every file.
- **Every edge names its posts.** `edges_*.event_id` is always a row of `events`: the carrier's first post of the value (relay), the answer's report post (exposure), the citing post (citation) or the reply (reply). `src_event_id` is the source's post: the parent's latest post on the page, the originator's first post for a cross-page hop, the first public copy, or the post replied to. Exposure edges also carry `claim_id`. Earlier runs stored the claim id in an exposure edge's `event_id`; read `claim_id` for it now. `value_norm` holds the comparison key for every kind (the first number of a multi-number value), so edges join `chains_*.value_key`.
- **Agent-written strings are data.** Author names, channels and text come from the agents, so ingest replaces lone surrogates (a truncated emoji's JSON escape, which Parquet cannot store) with U+FFFD in every string, removes control characters (C0, DEL, C1) from `author_raw`, `author_alt`, `channel`, `event_id`, `parent_id` and the roster's and directory's names and roles (a tab, newline or return becomes a space there, so a name cannot print a line of its own), and turns the ones XML forbids into a space in `text`; C1 stays in text, since XML allows it and it is how a mis-decoded dash reads (`â\x80\x93`, 46 wiki posts). profile.json's `warnings` and the report count the strings changed per column. GraphML writing passes node ids and attributes through the same filter, for runs ingested before it. `trace`, `agent` and `inspect` print control and bidi-override characters as escapes (`\x1b`, `\u202e`), so a name cannot retitle or clear the terminal. `export` and `crosssite` refuse an `-o` that is the run they read. Every text file is read and written as UTF-8 whatever the locale (a Windows or C-locale console included), and a console whose encoding lacks a character prints it as an escape instead of failing.
